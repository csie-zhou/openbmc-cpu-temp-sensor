## 2. Day 3 — Boot QEMU

### 2.1 Install QEMU

```bash
sudo apt install -y qemu-system-arm

# Verify the romulus machine is available
qemu-system-arm -M help | grep romulus
# → romulus-bmc         ASPEED Romulus BMC (ARM926EJ-S)
```

### 2.2 Write start_qemu.sh

Create this script in your project root and commit it to GitHub later —
it is part of your demo artifact.

```bash
cat > ~/openbmc/start_qemu.sh << 'EOF'
#!/usr/bin/env bash
# start_qemu.sh — Boot OpenBMC Romulus in QEMU
# Usage: ./start_qemu.sh [path-to-image]

IMAGE="${1:-$(ls ~/openbmc/build/tmp/deploy/images/romulus/obmc-phosphor-image-romulus.static.mtd 2>/dev/null | head -1)}"

if [ -z "$IMAGE" ]; then
  echo "ERROR: No .mtd image found. Run 'bitbake obmc-phosphor-image' first."
  exit 1
fi

echo "Booting: $IMAGE"
echo "bmcweb will be available at: https://localhost:2443"
echo "Login: root / 0penBmc"
echo "Press Ctrl-A then X to quit QEMU."
echo ""

qemu-system-arm \
  -M romulus-bmc \
  -nographic \
  -drive file="${IMAGE}",format=raw,if=mtd \
  -net nic \
  -net user,hostfwd=tcp:127.0.0.1:2443-:443,hostfwd=tcp:127.0.0.1:2022-:22
EOF

chmod +x ~/openbmc/start_qemu.sh
```

**What the flags mean:**

| Flag | Meaning |
|---|---|
| `-M romulus-bmc` | Emulate the ASPEED AST2500 Romulus BMC board |
| `-nographic` | No GUI window — use serial console in the terminal |
| `-drive file=...,if=mtd` | Mount the `.mtd` file as NOR flash |
| `hostfwd=tcp:...:2443-:443` | Forward host port 2443 → guest HTTPS port 443 |
| `hostfwd=tcp:...:2022-:22` | Forward host port 2022 → guest SSH port 22 |

### 2.3 Boot and log in

```bash
~/openbmc/start_qemu.sh
```

You will see the U-Boot bootloader, then the Linux kernel boot log, then
the OpenBMC login prompt. This takes about **60–90 seconds**.

```
...
OpenBMC Release v2.xx
romulus login:
```

Log in:

```
login:    root
password: 0penBmc
```

> **Note:** The password is the digit zero, not the letter O — `0penBmc`.

Once logged in, check that bmcweb is running:

```bash
systemctl status bmcweb
# Should show: active (running)

ip a
# Note the IP address on eth0 — it will be something like 10.0.2.15
# But you always connect via localhost:2443 from your host machine
```

Leave this terminal running QEMU. Open a **second terminal** on your host
for all `curl` commands.

### 2.4 Verify bmcweb is running

From your **host machine** (second terminal):

```bash
curl -k -u root:0penBmc https://localhost:2443/redfish/v1/

# Expected: a large JSON object starting with:
# { "@odata.type": "#ServiceRoot.v1_10_0.ServiceRoot", ... }
```

If this returns JSON, your environment is working. Move to Day 4.

## 3. Day 4 — Explore the Live Redfish API

Set this alias in your host terminal to save typing:

```bash
alias bmc='curl -sk -u root:0penBmc'
```

### 3.1 curl the API root

```bash
bmc https://localhost:2443/redfish/v1/ | python3 -m json.tool
```

Note the top-level collections: `Systems`, `Chassis`, `Managers`, `AccountService`.
Your sensor lives under `Chassis`.

### 3.2 Walk the Chassis subtree

```bash
# List chassis instances
bmc https://localhost:2443/redfish/v1/Chassis | python3 -m json.tool

# Inspect Chassis/chassis (Romulus uses "chassis" not "1")
bmc https://localhost:2443/redfish/v1/Chassis/chassis | python3 -m json.tool

# List sensors collection
bmc https://localhost:2443/redfish/v1/Chassis/chassis/Sensors | python3 -m json.tool
```

> **Important:** Romulus uses the chassis ID `"chassis"` (lowercase), not `"1"`.
> Your custom endpoint will follow the same convention:
> `/redfish/v1/Chassis/chassis/Sensors/temperature/cpu_temp`

### 3.3 Inspect an existing sensor

```bash
# List all sensor members in the collection
bmc https://localhost:2443/redfish/v1/Chassis/chassis/Sensors \
  | python3 -m json.tool | grep "@odata.id"

# Pick one and inspect it in full
bmc https://localhost:2443/redfish/v1/Chassis/chassis/Sensors/temperature/pcie_temp0 \
  | python3 -m json.tool
```

A typical sensor response looks like:

```json
{
    "@odata.id": "/redfish/v1/Chassis/chassis/Sensors/temperature/pcie_temp0",
    "@odata.type": "#Sensor.v1_2_0.Sensor",
    "Id": "pcie_temp0",
    "Name": "pcie_temp0",
    "ReadingType": "Temperature",
    "Reading": 28.0,
    "ReadingUnits": "Cel",
    "Status": {
        "Health": "OK",
        "State": "Enabled"
    }
}
```

This is **exactly the schema you will replicate** for your `cpu_temp` sensor.
Study every field — you will need to produce all of them from C++.

### 3.4 Map the full Sensors collection

```bash
# Save a snapshot of the full Sensors list for reference
bmc https://localhost:2443/redfish/v1/Chassis/chassis/Sensors \
  | python3 -m json.tool > ~/sensors_snapshot.json

cat ~/sensors_snapshot.json
```

Count how many sensors exist and note their naming convention:
`temperature/`, `power/`, `voltage/`. Your sensor will follow the
`temperature/` prefix.

## 4. Day 5 — Study bmcweb Source

### 4.1 Find the fetched bmcweb source

BitBake has already downloaded and unpacked the bmcweb source during the build.
Find it:

```bash
find ~/openbmc/build/tmp/work -type d -name "bmcweb" 2>/dev/null | head -5

# It will be something like:
# ~/openbmc/build/tmp/work/arm1176jzs-openbmc-linux-gnueabi/bmcweb/
#   1.0+gitAUTOINC+<commit>-r1/git/

# Set a convenient variable
BMCWEB=$(find ~/openbmc/build/tmp/work -path "*/bmcweb/1.0+git/sources/bmcweb*" -maxdepth 6 -type d 2>/dev/null | head -1)
echo $BMCWEB
```

The key files you need:

```bash
ls $BMCWEB/redfish-core/lib/
# Look for: sensors.hpp  (singular — this is where sensor routes live)
# Also:     chassis.hpp, manager.hpp, service_root.hpp
```

### 4.2 Understand the route registration pattern

Open `sensors.hpp` and look at how an existing sensor handler is registered:

```bash
grep -n "BMCWEB_ROUTE\|requestRoutes\|handleSensor" \
  $BMCWEB/redfish-core/lib/sensors.hpp | head -30
```

The pattern in bmcweb is:

```cpp
inline void handleSensorGet(App& app, const crow::Request& req,
                            const std::shared_ptr<bmcweb::AsyncResp>& asyncResp,
                            const std::string& chassisId,
                            const std::string& sensorId)
{
    // handler body
}

inline void requestRoutesSensor(App& app)
{
    BMCWEB_ROUTE(app, "/redfish/v1/Chassis/<str>/Sensors/<str>/")
        .privileges(redfish::privileges::getSensor)
        .methods(boost::beast::http::verb::get)(
            std::bind_front(sensors::handleSensorGet, std::ref(app)));
}
```

Key components:

| Component | Purpose |
|---|---|
| `handleSensorGet(...)` | Separate named function containing the handler logic |
| `requestRoutesSensor(app)` | Registers the URL pattern and binds the handler |
| `BMCWEB_ROUTE(app, "/path/")` | Register URL pattern with trailing slash |
| `.privileges(...)` | Access control — `getSensor` for read-only |
| `.methods(http::verb::get)` | HTTP GET only |
| `std::bind_front(handler, std::ref(app))` | Connects the handler function to the route |
| `asyncResp` | Async response object — write your JSON into `asyncResp->res.jsonValue` |
| `chassisId`, `sensorId` | URL path parameters captured from `<str>` placeholders |

Routes are activated in `redfish-core/src/redfish.cpp`. Confirm the registration location:
```bash
grep -n "requestRoutesSensor" $BMCWEB/redfish-core/src/redfish.cpp
```

### 4.3 Trace an existing sensor handler end-to-end

Look specifically for how the JSON response is built:

```bash
grep -n "asyncResp->res.jsonValue" \
  $BMCWEB/redfish-core/lib/sensor.hpp | head -20
```

You will see patterns like:

```cpp
asyncResp->res.jsonValue["@odata.type"] = "#Sensor.v1_2_0.Sensor";
asyncResp->res.jsonValue["@odata.id"]   = req.url();
asyncResp->res.jsonValue["Reading"]     = someDoubleValue;
asyncResp->res.jsonValue["ReadingType"] = "Temperature";
asyncResp->res.jsonValue["ReadingUnits"]= "Cel";
asyncResp->res.jsonValue["Status"]["Health"] = "OK";
asyncResp->res.jsonValue["Status"]["State"]  = "Enabled";
```

This is `nlohmann::json` — assigning values by key directly into the JSON
object. No serialization needed; bmcweb handles the HTTP response automatically.

### 4.4 Identify your insertion point

In the modern bmcweb codebase there is one clear pattern: handler functions
live in `sensors.hpp` and are registered in `redfish.cpp`. Follow the same
structure.

**Step 1 — Find the end of `sensors.hpp`:**
```bash
wc -l $BMCWEB/redfish-core/lib/sensors.hpp
tail -20 $BMCWEB/redfish-core/lib/sensors.hpp
```

**Step 2 — Find where to register in `redfish.cpp`:**
```bash
grep -n "requestRoutesSensor" $BMCWEB/redfish-core/src/redfish.cpp
```

You will see output like:
```
223:    requestRoutesSensorCollection(app);
224:    requestRoutesSensor(app);
```

Your new `requestRoutesRpiSensor(app)` call goes on line 225, immediately after.

**Step 3 — Confirm the include chain:**
```bash
grep -n "sensors.hpp" $BMCWEB/redfish-core/src/redfish.cpp
```

Since `sensors.hpp` is already included, you only need to add your handler
function at the bottom of `sensors.hpp` and one call line in `redfish.cpp`.
No new files needed.

### 4.5 Set up the mock thermal sensor

The QEMU Romulus machine does not emulate the AST2500's thermal ADC hardware,
so the Linux thermal subsystem never loads and `/sys/class/thermal/` does not exist:

```bash
# Inside QEMU — confirms the problem
ls /sys/class/thermal/
# → ls: /sys/class/thermal/: No such file or directory
```

Your handler instead reads from `/tmp/cpu_temp` — a file with the same
millidegree integer format as a real sysfs thermal zone.
On real hardware, swapping the path is a one-line change:

```cpp
// Real hardware (not available in QEMU):
// constexpr const char* thermalPath = "/sys/class/thermal/thermal_zone0/temp";

// Mock sensor for QEMU development:
constexpr const char* thermalPath = "/tmp/cpu_temp";
```

The `ifstream` read, the divide-by-1000, and all JSON fields stay identical.

#### Step 1: Static baseline — confirm the path works

```bash
# Inside QEMU (root@romulus)
echo "45000" > /tmp/cpu_temp
cat /tmp/cpu_temp
# → 45000  (= 45.0°C)
```

This is enough to verify the endpoint in Day 6. Come back to Step 2 once
the handler is working.

#### Step 2: Dynamic simulation — temperature that responds to CPU load

A static value is fine for basic testing but not useful for a demo.
The script below reads real CPU load from `/proc/stat` and derives a
simulated temperature (35°C idle, rising toward 80°C at full load):

```bash
# Inside QEMU (root@romulus)
cat > /tmp/mock_thermal.sh << 'EOF'
#!/bin/sh
# mock_thermal.sh — dynamic CPU temperature simulation
# Reads /proc/stat CPU load, writes millidegree value to /tmp/cpu_temp
# Formula: BASE(35000) + cpu_load_pct * SCALE(450)
# Range: ~35 C idle  ->  ~80 C at 100% load

BASE=35000
SCALE=450
prev_idle=0
prev_total=0

while true; do
    read -r cpu user nice system idle iowait irq softirq rest < /proc/stat
    total=$((user + nice + system + idle + iowait + irq + softirq))
    diff_total=$((total - prev_total))
    diff_idle=$((idle  - prev_idle))

    if [ "$diff_total" -gt 0 ]; then
        load_pct=$(( (diff_total - diff_idle) * 100 / diff_total ))
    else
        load_pct=0
    fi

    echo $(( BASE + load_pct * SCALE )) > /tmp/cpu_temp

    prev_total=$total
    prev_idle=$idle
    sleep 2
done
EOF

chmod +x /tmp/mock_thermal.sh
```

Start it in the background:

```bash
/tmp/mock_thermal.sh &
sleep 3 && cat /tmp/cpu_temp
# → ~35000 at idle
```

> It's based on QEMU's virtual CPU load — specifically `/proc/stat` inside the QEMU guest (romulus), so it is not the Windows CPU.
The chain is:
```
Windows CPU (real hardware)
    ↓
WSL2 Ubuntu (uses some of the Windows CPU)
    ↓
QEMU process (runs inside Ubuntu, uses some of Ubuntu's CPU)
    ↓
romulus guest OS (sees a virtual CPU)
    ↓
/proc/stat inside romulus ← this is what mock_thermal.sh reads
```

But Windows CPU gets busy, QEMU gets less CPU time from the host, which can also affect the guest's `/proc/stat` idle values.

#### Step 3: Verify the value is dynamic

Open two terminals to monitor in reality, but in QEMU, we will run both commands in the same terminal.

```bash
# Confirm mock_thermal.sh is still running (started in Step 2)
jobs
# → Should show [1] Running /tmp/mock_thermal.sh
# If not running, restart it:
# /tmp/mock_thermal.sh &

# Check baseline temperature
sleep 2 && cat /tmp/cpu_temp
# → ~35000-40000 at idle

# Generate CPU load
dd if=/dev/zero of=/dev/null bs=1M &
dd if=/dev/zero of=/dev/null bs=1M &

# Check temperature under load
sleep 5 && cat /tmp/cpu_temp
# → ~80000 at full load

# Kill load
kill %3 %4

# Check temperature after load removed
sleep 5 && cat /tmp/cpu_temp
# → back to ~35000-40000
```

Explain:
```
dd (CPU stressor)          mock_thermal.sh (reads /proc/stat)
      ↓                              ↓
Loads the virtual CPU    →    sees CPU% go up    →    writes higher value to /tmp/cpu_temp
                                                              ↓
                                                    bmcweb handler reads /tmp/cpu_temp
                                                              ↓
                                                    Redfish API returns higher Reading
                                                              ↓
                                                    curl on host sees temperature rise
```

So `dd` is just the thing that generates heat. `mock_thermal.sh` is the thermometer. `bmcweb/Redfish` is the remote monitoring interface that exposes that temperature over HTTP.

In a real server, `dd` would be replaced by actual workload (database queries, video encoding, etc.), and `/tmp/cpu_temp` would be replaced by a real hardware sensor at `/sys/class/thermal/thermal_zone0/temp`. The `bmcweb/Redfish` layer stays identical.

##### (Two Terminal Version -- Not Used)

**Terminal 1 — watch the value:**
```bash
watch -n 2 cat /tmp/cpu_temp
```

**Terminal 2 — generate CPU load:**
```bash
dd if=/dev/zero of=/dev/null bs=1M &
dd if=/dev/zero of=/dev/null bs=1M &
# Watch terminal 1 — value should climb toward 60000–70000
kill %1 %2
# Value falls back to ~35000
```

> **Persistence note:** `/tmp/` and `/tmp/` are cleared on each
> fresh QEMU boot. After every new image flash, recreate `mock_thermal.sh`
> and run it again. Day 9–10 covers baking it into the image permanently.

## 5. Concepts: Redfish Architecture & the QEMU Hardware Gap

### The Redfish URL hierarchy

```
/redfish/v1/                          ← ServiceRoot
├── Chassis/
│   └── chassis/                      ← ChassisCollection member
│       ├── Sensors/                  ← SensorCollection
│       │   └── temperature/
│       │       └── cpu_temp          ← YOUR new sensor  ←──────┐
│       └── Thermal/                                             │
├── Systems/                          You are adding this ───────┘
└── Managers/
```

Note: on real hardware this collection would already contain sensors from
`phosphor-hwmon`. In QEMU the collection is empty — your sensor will be
the only member, which makes it easy to verify.

### Why the Sensors collection is empty in QEMU

On a real server the data flow is:

```
Physical chip (I2C ADC)
        │
        ▼
phosphor-hwmon daemon  ←── reads hardware
        │
        ▼
D-Bus  ←── sensor values published here
        │
        ▼
bmcweb  ←── reads D-Bus, serves Redfish
        │
        ▼
GET /Chassis/chassis/Sensors  →  populated list
```

In QEMU there is no physical chip, so `phosphor-hwmon` has nothing to read,
D-Bus has no sensor objects, and the collection is empty.

Your handler **bypasses this entire chain** — it reads a file directly
and writes the JSON response itself. This is why it works in QEMU where
the D-Bus path fails.

### The mock sensor approach

Rather than fighting the missing hardware, you use a **mock sensor file**:

```
/tmp/mock_thermal.sh  ←── running in background inside QEMU
        │  reads /proc/stat (real CPU load)
        │  computes simulated temperature
        │  writes millidegrees to file every 2s
        ▼
/tmp/cpu_temp  ←── your sensor file (same format as real sysfs)
        │
        ▼
bmcweb C++ handler  ←── std::ifstream reads /tmp/cpu_temp
        │
        ▼
GET /Chassis/chassis/Sensors/temperature/cpu_temp  →  dynamic Reading value
```

The millidegree integer format (`45000` = 45.0°C) is identical to the real
Linux sysfs thermal zone interface. Your C++ code is portable — swapping
`/tmp/cpu_temp` for `/sys/class/thermal/thermal_zone0/temp` is a one-line
change when deploying on real hardware.

### bmcweb request lifecycle

```
HTTP GET request arrives
        │
        ▼
Crow router matches URL pattern
        │
        ▼
Privilege check (getSensor)
        │
        ▼
Your handler function is called
        │
        ├─ Open /tmp/cpu_temp with std::ifstream
        ├─ Read integer millidegrees
        ├─ Divide by 1000.0 → Celsius double
        ├─ Build nlohmann::json response object
        └─ asyncResp->res.jsonValue = ...
                │
                ▼
        bmcweb serialises JSON → HTTP 200 response
```

### Why async?

bmcweb uses Boost.Asio for async I/O. The `AsyncResp` object keeps the
response open until all async operations complete. For your handler — which
only does a synchronous file read — you populate the response synchronously
and let `asyncResp` go out of scope, which triggers the send automatically.
You do not need to understand the full async model for this project.

## 6. Troubleshooting

### QEMU won't start — "romulus-bmc not found"

```bash
# Confirm your qemu-system-arm version supports romulus
qemu-system-arm --version
# Need 4.0+; ubuntu 22.04 ships 6.x which is fine

qemu-system-arm -M help | grep romulus
```

If romulus is missing, your qemu is too old:

```bash
sudo apt install -y qemu-system-arm   # upgrades if available
# Or build from source: https://www.qemu.org/download/
```

### QEMU boots but login prompt never appears

The serial output may be on a different device. Try:

```bash
qemu-system-arm \
  -M romulus-bmc \
  -nographic \
  -drive file="${IMAGE}",format=raw,if=mtd \
  -net nic \
  -net user,hostfwd=tcp:127.0.0.1:2443-:443 \
  -serial mon:stdio
```

### curl returns "Connection refused"

bmcweb takes ~30 seconds to start after Linux boots. Wait and retry.

```bash
# Poll until bmcweb is up
until curl -sk -u root:0penBmc https://localhost:2443/redfish/v1/ > /dev/null; do
  echo "Waiting for bmcweb..."; sleep 5
done
echo "bmcweb is up"
```

### curl returns "SSL handshake failed"

Use `-k` flag to skip certificate verification (bmcweb uses a self-signed cert):

```bash
curl -k -u root:0penBmc https://localhost:2443/redfish/v1/
#    ^^
```

### Sensor path is different on your Romulus build

If `/redfish/v1/Chassis/chassis/Sensors` returns 404:

```bash
# Find the actual chassis ID
bmc https://localhost:2443/redfish/v1/Chassis | python3 -m json.tool
# Look for "Members" array → "@odata.id" values
```

Use whatever chassis ID is listed in your build.
