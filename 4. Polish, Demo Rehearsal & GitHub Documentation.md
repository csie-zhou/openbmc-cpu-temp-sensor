With both sensors you have a real dashboard story:

**Step 2: Add the C++ handler for cpu_freq**

In `$BMCWEB/redfish-core/lib/sensors.hpp`, add a second handler pair before `} // namespace redfish`,
immediately after `requestRoutesCpuTemp`:

```cpp
inline void handleCpuFreqGet(
    App& /*app*/, const crow::Request& /*req*/,
    const std::shared_ptr<bmcweb::AsyncResp>& asyncResp,
    const std::string& chassisId)
{
    if (chassisId != "chassis")
    {
        messages::resourceNotFound(asyncResp->res, "Chassis", chassisId);
        return;
    }

    // /tmp/cpu_freq: kHz integer (same format as sysfs cpufreq)
    // Real hardware: /sys/devices/system/cpu/cpu0/cpufreq/scaling_cur_freq
    std::ifstream freqFile("/tmp/cpu_freq");
    if (!freqFile.is_open())
    {
        asyncResp->res.result(
            boost::beast::http::status::service_unavailable);
        asyncResp->res.jsonValue["error"]["code"] =
            "Base.1.0.ServiceTemporarilyUnavailable";
        asyncResp->res.jsonValue["error"]["message"] =
            "Frequency sensor not available";
        return;
    }

    int khz = 0;
    freqFile >> khz;
    const double mhz = static_cast<double>(khz) / 1000.0;

    nlohmann::json& j   = asyncResp->res.jsonValue;
    j["@odata.type"]    = "#Sensor.v1_2_0.Sensor";
    j["@odata.id"]      =
        "/redfish/v1/Chassis/chassis/Sensors/frequency/cpu_freq";
    j["Id"]             = "cpu_freq";
    j["Name"]           = "CPU Frequency";
    j["ReadingType"]    = "Frequency";
    j["Reading"]        = mhz;
    j["ReadingUnits"]   = "MHz";
    j["Status"]["Health"] = "OK";
    j["Status"]["State"]  = "Enabled";
}

inline void requestRoutesCpuFreq(App& app)
{
    BMCWEB_ROUTE(app,
                 "/redfish/v1/Chassis/<str>/Sensors/frequency/cpu_freq")
        .privileges(redfish::privileges::getSensor)
        .methods(boost::beast::http::verb::get)(
            std::bind_front(handleCpuFreqGet, std::ref(app)));
}
```

**Step 6: Create start_demo.sh (after build finishes)**

```bash
cat > ~/openbmc/start_demo.sh << 'EOF'
#!/usr/bin/env bash
# start_demo.sh — Boot QEMU and start the mock thermal sensor

IMAGE="$(dirname "$0")/build/tmp/deploy/images/romulus/obmc-phosphor-image-romulus.static.mtd"

qemu-system-arm \
  -M romulus-bmc \
  -nographic \
  -drive file="$IMAGE",format=raw,if=mtd \
  -net nic \
  -net user,hostfwd=tcp:127.0.0.1:2443-:443,hostfwd=tcp:127.0.0.1:2222-:22 &

QEMU_PID=$!
echo "QEMU started (PID $QEMU_PID). Waiting for boot..."
sleep 90

ssh -o StrictHostKeyChecking=no -p 2222 root@localhost << 'ENDSSH'
cat > /tmp/mock_thermal.sh << 'SCRIPT'
#!/bin/sh
TEMP_BASE=35000
TEMP_SCALE=450
FREQ_BASE=600000
FREQ_SCALE=6000
prev_idle=0
prev_total=0
while true; do
    read -r cpu user nice system idle iowait irq softirq rest < /proc/stat
    total=$((user + nice + system + idle + iowait + irq + softirq))
    diff_total=$((total - prev_total))
    diff_idle=$((idle - prev_idle))
    [ "$diff_total" -gt 0 ] && \
        load_pct=$(( (diff_total - diff_idle) * 100 / diff_total )) || \
        load_pct=0
    [ "$load_pct" -lt 0   ] && load_pct=0
    [ "$load_pct" -gt 100 ] && load_pct=100
    echo $(( TEMP_BASE + load_pct * TEMP_SCALE )) > /tmp/cpu_temp
    echo $(( FREQ_BASE + load_pct * FREQ_SCALE )) > /tmp/cpu_freq
    prev_total=$total
    prev_idle=$idle
    sleep 2
done
SCRIPT
chmod +x /tmp/mock_thermal.sh
/tmp/mock_thermal.sh &
echo "mock_thermal.sh started"
ENDSSH

echo "Demo ready at https://localhost:2443"
echo "Login: root / 0penBmc"
wait $QEMU_PID
EOF

chmod +x ~/openbmc/start_demo.sh
```

> For interview demos, boot QEMU the night before and leave it running.
> You only need to recreate the script when you flash a new image.
> In production, this would be a systemd service baked into the image
> via a Yocto recipe — the same way OpenBMC manages all its native services.

### 2.2 The live dashboard — redfish_monitor.py

This is the centrepiece of your demo. A Python terminal dashboard that
polls both Redfish endpoints every 2 seconds and renders real-time bar
graphs, sparkline history, and health indicators — zero third-party
dependencies, stdlib only.

It lives here:
```bash
redfish_monitor.py (host)
        |
        | HTTPS to localhost:2443
        |
    QEMU port forward (2443 → 443 inside QEMU)
        |
    bmcweb (inside QEMU)
        |
    reads /tmp/cpu_temp and /tmp/cpu_freq
        |
    mock_thermal.sh writes those files
```

Save this as `scripts/redfish_monitor.py` in your project repo and run it
on your host machine while QEMU is running:


### 3.2 README template

````markdown
# OpenBMC Custom Redfish Sensor Dashboard — QEMU Romulus

Extends [OpenBMC](https://github.com/openbmc/openbmc)'s **bmcweb** HTTP
service with two custom Redfish sensor endpoints, backed by a `mock_thermal.sh`
simulation and visualised by a live terminal dashboard (`redfish_monitor.py`).
Runs entirely on QEMU — no hardware required.

## What this project demonstrates

- **BMC firmware development** — adding Redfish sensor resources to bmcweb (C++)
  using the modern handler pattern (`handleCpuTempGet`, `requestRoutesCpuTemp`)
- **Redfish protocol** — two DSP0268-compliant Sensor resources across the
  `temperature/` and `frequency/` subtrees
- **Yocto / BitBake** — patching upstream recipes via `.bbappend` without forking
- **Hardware abstraction** — mock sensors with the same sysfs integer format;
  one-line path swap to deploy on real AST2500 hardware
- **Redfish client development** — stdlib Python dashboard consuming the live API

## New endpoints

```
GET /redfish/v1/Chassis/chassis/Sensors/temperature/cpu_temp
GET /redfish/v1/Chassis/chassis/Sensors/frequency/cpu_freq
```

Both return Redfish DSP0268-compliant JSON. Values are dynamic — they rise
under CPU load and return to idle levels, driven by `mock_thermal.sh`.

## Live dashboard

```bash
python3 scripts/redfish_monitor.py
```

Polls both endpoints every 2 seconds. Shows real-time bar graphs, sparkline
history, min/avg/max session stats, and health indicators (OK / WARNING / CRITICAL).
No third-party dependencies — stdlib only.

## Architecture

```
[ redfish_monitor.py ]  ← Redfish client (runs on host)
         | HTTPS :2443
         v
[ bmcweb C++ ]  ← handleCpuTempGet + handleCpuFreqGet added to sensors.hpp
         |         registered in redfish.cpp
         v
[ /tmp/cpu_temp ]  ← millidegrees Celsius
[ /tmp/cpu_freq ]  ← kHz
         ^
[ mock_thermal.sh ]  ← reads /proc/stat, writes both files every 2s

All running inside QEMU emulating ASPEED AST2500 Romulus BMC
Built with Yocto/BitBake — obmc-phosphor-image, meta-ibm/meta-romulus

Note: QEMU omits ADC hardware emulation so /sys/class/thermal/ is absent.
On real hardware, swap /tmp/cpu_temp for /sys/class/thermal/thermal_zone0/temp
and /tmp/cpu_freq for /sys/devices/system/cpu/cpu0/cpufreq/scaling_cur_freq.
The millidegree/kHz integer format is identical in both cases.
```
````

### 4.3 Interview Q&A prep

**Q: What is a BMC and what does it do?**

A BMC is an independent SoC on a server motherboard that manages hardware
out-of-band — independently of the main CPU. It handles power state,
thermal monitoring, fan control, and remote management, and stays powered
even when the main CPU is off. OpenBMC is the open-source Linux-based
firmware stack for BMCs; bmcweb is its Redfish HTTP server.

**Q: What is Redfish and why does it matter?**

Redfish is the DMTF standard RESTful management API replacing IPMI in
modern servers. IPMI is a 30-year-old binary protocol over UDP; Redfish
uses JSON over HTTPS — human-readable, schema-validated, and extensible.
My implementation follows the DSP0268 schema, the same schema a production
BMC would serve.

**Q: Why did you use QEMU instead of real hardware?**

QEMU Romulus is the official, first-class OpenBMC development target —
OpenBMC developers themselves use it day-to-day. It emulates an ASPEED
AST2500 used in IBM Power servers, so the firmware stack is identical.
QEMU also means the project is reproducible by anyone and demoed on a
laptop without hardware setup.

**Q: QEMU doesn't have real thermal hardware — how did you handle that?**

QEMU doesn't emulate the AST2500's ADC, so `/sys/class/thermal/` is absent.
I used a mock sensor at `/tmp/cpu_temp` backed by a shell script that reads
real CPU load from `/proc/stat` and derives a temperature in the same
millidegree integer format as the real sysfs thermal zone. On real hardware,
swapping the path is a one-line change — the handler code is identical.
This is standard hardware abstraction practice in embedded firmware development.

**Q: Explain the Yocto .bbappend pattern.**

Yocto's layer model lets you extend upstream recipes without forking them.
My `.bbappend` in `meta-ibm/meta-romulus` uses `FILESEXTRAPATHS:prepend`
to point BitBake at my patch directory, and `SRC_URI +=` to add the patch
to the source list. During `do_patch`, BitBake applies it on top of the
upstream bmcweb before compiling. The upstream recipe stays clean and
upgradeable — the same pattern used in production BMC firmware teams.

**Q: How does your handler work at the code level?**

I added two handler pairs to `sensors.hpp` following the modern bmcweb
pattern: `handleCpuTempGet` and `handleCpuFreqGet` contain the logic;
`requestRoutesCpuTemp` and `requestRoutesCpuFreq` register the
`BMCWEB_ROUTE` macros and wire them via `std::bind_front`. Each handler
validates the chassis ID, opens its sensor file with `std::ifstream`,
reads an integer (millidegrees or kHz), converts to the display unit,
and populates `nlohmann::json` with all required Redfish Sensor schema
fields. If the file is unreadable it returns HTTP 503. Both functions
are registered in `redfish.cpp` alongside the existing route registrations.

**Q: What is redfish_monitor.py and why did you build it?**

It's a stdlib Python dashboard that polls both Redfish endpoints every
2 seconds and renders a terminal UI with bar graphs, sparkline history,
and health indicators. I built it because showing a live monitoring client
consuming the API is more compelling than a static curl output — it
demonstrates the full picture: firmware implementation on one side, API
consumer on the other. In production, this role is played by agents like
Grafana exporters or cloud management platforms. The dashboard is the
project's demo centrepiece.
